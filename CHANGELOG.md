# Changelog

## 2.0.0 — 2026-11-22

- **Refactor: the bridge keeps its own state in `claude-bridge/` instead of pi's agent dir root** — usage snapshots (`usage/<account>.json`), session mirrors (`mirrors/`) and the debug and diagnostics logs (`logs/bridge.log`, `logs/diag.log`, `logs/cc-cli-logs/`) used to sit straight in `~/.pi/agent` beside pi's own files, one usage file per account. Activation moves what an earlier version left in the root (a file already in `claude-bridge/` wins; a log is never deleted), removes the session store a removed module left in `claude-bridge/sessions/`, and drops usage snapshots no process refreshed in 30 days. `claude-bridge.json` stays in the root with pi's other configuration, and `CLAUDE_BRIDGE_DEBUG_PATH` still names the debug log.
- **Fix: the Gentle Shell usage bar follows a subagent's usage while it works** — each subagent runs in its own `pi` process, so the plan usage its Claude Code reported reached only that process, and the parent's 5h bar stood still until the parent's own next request (after the subagent returned). Every bridge now writes its latest rate-limit event to its account's `claude-bridge/usage/<hash>.json` in pi's agent dir (atomically, named by a hash of `CLAUDE_CODE_OAUTH_TOKEN`, so a subagent on another pi-claude-accounts account neither moves nor hides the parent's bar), and the interactive parent watches its account's file and re-registers a Gentle Shell usage source (`gentle-pi:usage-source/v1`), which refreshes the bar at once. Without Gentle Shell the event goes nowhere and nothing else changes. Reports arrive after the response they measured, so a later report can carry an older measurement: within one window (same reset time) the bar shows the highest usage seen for the account, including a report the parent held while it waited on a tool; a new window replaces it.
- **Fix: a tool call answered by another provider no longer leaves Claude Code waiting for good** — when pi switched to a non-Claude model while a Claude tool ran, the tool result went to that provider and never reached the Claude Code query parked on the call, which then lived until the pi session ended (one leaked Claude Code process per switch). Every later Claude prompt in that session saw it running and was treated as nested: system prompt changes never reached Claude, and a turn continuing at a tool result wrote on stdin again, bringing back "No response requested." (upstream #274). The next Claude prompt now discards a parked query whose call already has a result in pi's history, and rebuilds from that history.
- **Fix: a model switched while a tool runs serves the rest of the turn (upstream #273)** — the result of a tool call went to the Claude Code query already running, which kept the model it was started with, so a switch (`/model` while a tool runs, or a router picking a stronger model after the first results) only took effect at the next prompt. The bridge now calls the SDK's `setModel` on that query before delivering the result, which Claude Code applies to the same turn's next request (pinned in `tests/int-cc-contracts.mjs`, `[1m]` models included), and labels and prices the continuation with the new model. Before, the continuation was also labeled with the newly requested model though the old one served it. If Claude Code refuses the switch, the turn finishes on the old model, labeled with that model, and the switch takes effect at the next prompt; no model refused in a query is tried again at its later tool results, so a long turn makes one failed validation request per model, not one per tool call. The result waits at most 15 s for the switch, which makes a validation request to the API; a switch that lands later serves the rest of the turn from then on. The effort the bridge computes for the new model goes with the switch (`applyFlagSettings`, or the model's default when it computes none). Thinking cannot follow: Claude Code keeps the thinking a query started with, so when the two models need different thinking settings (thinking off, from a model that can disable it to one that cannot, such as Haiku 5.5 to Opus 5.5) the turn finishes on the old model and the switch takes effect at the next prompt. A thinking level changed while a tool runs (same model) now sets the new effort for the rest of the turn the same way, before the result goes in and within the same 15 s; before, the turn kept the effort it started with. Turning thinking on or off still waits for the next prompt, and an effort Claude Code refuses is not tried again in that query.
- **Fix: a turn continued at a tool result no longer gets "No response requested." (upstream #274)** — when a pi turn went on at a tool result with no Claude Code query parked on it (pi compacted mid-turn, pi or the host restarted mid-tool, or the bridge discarded the query), the bridge wrote its continue text on stdin as a new user message after the tool result; Claude Code then inserted a `<synthetic>` assistant "No response requested." between the two, and the model sometimes took that as its finished answer and ended the turn. Such a query now writes nothing on stdin: its child alone gets `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`, `CLAUDE_CODE_RESUME_PROMPT=<the continue text>` and `CLAUDE_CODE_RESUME_INTERRUPTED_TURN_MAX_AGE_MS=0`, so Claude Code resumes the turn itself, over a session file rebuilt to end at the tool result (never its own file after an abort or error, which can hold records past it). Every other query keeps `MAX_AGE_MS=1` and never inherits the two resume variables from pi's environment. If Claude Code shows no sign of working on the turn within 30 s (no request under way, no output, no retry), the old continue prompt is written after all, so the turn never hangs; a slow first response is not mistaken for silence, since Claude Code reports the request it starts. The Claude Code behavior is pinned in `tests/int-cc-contracts.mjs`.
- **Fix: the bash schema Claude reads no longer says "no default timeout" (upstream #270)** — the bridge runs a Claude model's bash call without `timeout` with 120 s, but the schema it advertised was pi's, which describes `timeout` as "(optional, no default timeout)", so a long command run without one ended with "Command timed out after 120 seconds". The bash tool Claude Code sees now describes `timeout` as "(optional; 120 when omitted)"; a `timeout` described otherwise gets "(120 when omitted)" appended. pi's own tool definition is unchanged. The changed tool definition misses the prompt cache once.
- **Fix: pi's whole system prompt reaches Claude, and turns no longer fail with "no capture for this N-char system prompt" (breaking, upstream #262, #37)** — the bridge looked each prompt up in captures recorded at `before_agent_start`/`agent_start`/`turn_start` and sent Claude Code only their portable parts (context files, skills, custom and appended prompts, sections), so a prompt nothing had recorded failed the turn: one an extension replaced, or a [nicobailon/pi-subagents](https://github.com/nicobailon/pi-subagents) background child (`async: true`, including `oracle` by default) sending its parent's prompt from another process. The bridge now forwards pi's prompt whole, as pi renders it (tools, rules, docs, context files, skills, extensions' sections, a subagent's wrapper), as the append to Claude Code's `claude_code` preset; `provider.systemPromptPreset: false` in the global config sends it alone as a plain string (upstream's `"claude_code"` and `null` are accepted too; any other value is reported once per process and ignored). Compaction and branch summaries still send pi's summarization prompt alone. Claude Code still loads no `CLAUDE.md`/`AGENTS.md` of its own. A prompt that changes between turns, or a changed `systemPromptPreset`, now takes effect: Claude Code re-sends the prompt a session was created with on every resume and ignores a new one (pinned in `tests/int-cc-contracts.mjs`), so before this a changed prompt never reached Claude. Like upstream's prompt digest, the bridge records a digest of the preset setting and the whole prompt with the session's mirror (`claude-bridge-mirrors/`, so it holds across `/reload` and a new process) and rebuilds Claude Code's session from pi's history when it differs, on every path that would resume: a plain resume, after an abort, a retry after an API error, and a `/fork`, which rebuilds instead of forking a parent made with another prompt. The rebuild re-caches the conversation once. A mirror written by an earlier version records no prompt, so a session continued after the update rebuilds once. pi 1.5.2's whole prompt (upstream's measurement) and a 104,653-character one from a setup with other extensions were served on the plan with Extra Usage off, after the preset and alone (`diag/EXTRA-USAGE-400.md`, "A real pi setup's whole prompt"). The capture code is gone, and with it the `claude-bridge-captures/` store in pi's agent dir, which an unreleased build kept for #37 and which held prompt text: activation now removes the directory (a failure goes to the debug log and never blocks activation). @gotgenes/pi-subagents no longer needs `promptInheritance: portable`. Breaking: Claude now sees pi's own tool, rule and documentation sections, and a session continued after the update is rebuilt and misses the prompt cache on its next turn.
- **Tests: the abort-resume contracts no longer read a user hook's request** — the two `CLAUDE_CODE_RESUME_INTERRUPTED_TURN_MAX_AGE_MS=1` contracts in `tests/int-cc-contracts.mjs` took the last stub request that mentioned their prompt, which on a machine with a Claude Code hook that runs a model (it inherits `ANTHROPIC_BASE_URL`) was the hook's request, not the resumed turn, so they failed with "the resumed request lost EARLIER-PROMPT". They now pick their own turn with `turnRequest`, like the other contracts.
- **Remove: the "Are you using a Max plan?" startup notice (upstream 2cd1051)** — it told every user without `provider.plan` to set `"max"` to unlock 1M context in Opus, but current Opus models get 1M on every plan (only Opus 4.6 depends on `plan`). The notice is gone, and with it the only reason the bridge wrote to its config: it no longer records `startupNoticeShown` in `claude-bridge.json` (a key left by an older version is ignored), so pi starting while the bridge rewrote the file can no longer read an empty config. The "no models available" error now names pi-ai 1.5.1 as the minimum.
- **Add: warn when a request is billed to Extra Usage with plan limits left (upstream f14f2ed)** — Claude Code reports such a request as `overageInUse` without `isUsingOverage`, and nothing told the user they were paying for it. The first such rate-limit event of a query now shows a warning: "Claude Code request billed to Extra Usage: no plan limit was reported as reached, so Anthropic may have read the system prompt as a third-party app, or this model needs usage credits on your plan". An "out of extra usage" error with no plan limit rejected first gets the same explanation. Neither appears when `longContextExtraUsage` is what enables the model's 1M context, since that request bills Extra Usage by choice.
- **Fix: a tool call Claude Code rejected itself hung the turn (upstream #218)** — when a permission rule or hook in `~/.claude/settings.json`, or input that is not JSON, made Claude Code reject a call it had already streamed to pi, it never called the bridge's MCP handler, so pi's result had nowhere to go and the turn stayed on "Working" until aborted. The bridge now notices Claude Code's own result for a call it never dispatched. A call rejected before pi was handed it (the usual case: a raw tab in an `edit` of tab-indented code, which failed subagents with "assistant reported an error (unavailable)") is taken out of the turn and the turn goes on: Claude Code tells the model why, as it does natively, and the model's retry reaches pi. A call rejected once pi has it ends the query and fails the turn with `Claude Code rejected pi's tool call "<name>" … Claude Code said: "<reason>"`; when pi is still running the call, its result ends the turn with that error instead. The session is rebuilt from pi's history on the next turn. Tool names now match exactly: a served name in the wrong case, which Claude Code rejects and retries, no longer reaches pi.
- **Remove: the system prompt guard; require pi 1.5.1 (upstream f14f2ed)** — the bridge refused a turn whose forwarded prompt carried pi's preamble at a line start or both `docs/custom-provider.md` and `docs/packages.md`, because Anthropic billed pi 1.4's harness as Extra Usage. Upstream measured pi 1.5.1's and 1.5.2's whole system prompt served on the plan, with the docs-path pair included, so the guard only refused turns that would work, such as a subagent that embeds its parent's prompt. Both halves of the guard (`src/fork-prompt-guard.ts` included) are gone, and the peer dependencies now require pi 1.5.1, whose prompt is the one measured.
- **Add: Claude Mythos 5.2 and 5.1, with 1M context (upstream #259)** — pi-ai leaves these access-gated models out, so `/model` never listed them. They are now added at the bottom of the list, each a copy of its Fable sibling's limits (Mythos 5.2 from Fable 5.2, 5.1 from 5.1), and sent as `[1m]`, which served 1M on Max in upstream's measurement. If pi-ai ever lists one, its own entry wins. Accounts outside Anthropic's Mythos programs get a 404 from Claude Code.
- **Tests: the abort-after-reload test no longer fails at random (#40)** — after a reload the bridge polls `/proc` and resumes as soon as the aborted CLI is a zombie, which can be before the test process sees the child's exit event; the test checked that event after the turn, so under CI load it failed though the bridge had waited. It now records, as the next query is created, whether the CLI is gone or a zombie.
- **Bump: develop and test against pi 1.5.1** — the dev dependencies were pinned at pi 1.2.0, so the checks that read pi's own code (the `streamFn` consumer inventory) were testing a pi nobody runs. They now run against 1.5.1: pi's three new `streamFn` mentions only mark a stream function for auth and never call it. `@earendil-works/pi-tui`, no longer imported, is dropped from the peer and dev dependencies.
- **Fix: the session mirror file is owner-only and safe to save from two windows** — `claude-bridge-mirrors/` files, which can hold an aborted prompt's text, were created with default permissions; they are now `0600` in a `0700` directory, and a directory an earlier version created is tightened to `0700` on the next save. Each process also writes its own temp file before the rename, so two pi windows saving the same session cannot leave a half-written mirror.
- **Fix: no false "malformed JSONL" warning for an empty rebuilt session** — a rebuild whose history converted to no records was reported as a broken session file, with a request to open an issue.
- **Fix: `@file` expansions survive a rebuild after a turn of several user messages** — Claude Code stores such a turn as one prompt, so every later prompt sat at a different position in its file than in pi's history, and each later `@file` expansion was dropped as "changed" on the next rebuild. Prompts are now matched by text from the recorded position; a text that more than one remaining prompt carries is still dropped rather than guessed.
- **Fix: a rebuild that fails no longer deletes Claude Code's session file** — a rebuild deleted the old session file before converting pi's history, so a conversion error (or a failed save) left no file, with the bridge still pointing at it and the carried `@file` expansions lost. The history is now converted first; if the save itself fails, the bridge forgets the session and rebuilds cleanly next turn.
- **Fix: an answer that arrived without stream events was shown twice** — when Claude Code delivered a turn's text only as an assistant message (a non-streaming fallback before any stream event), the result's copy of the same text was added as a second block, so pi stored and replayed the answer twice. The result text is now added only when no text block reached the turn.
- **Fix: a config file that is valid JSON but not an object no longer stops the extension loading** — a `.pi/claude-bridge.json` in a cloned repo (or the global config) holding `null` threw at activation, so no Claude model was registered. A file that is not a JSON object is now ignored like an unparseable one.
- **Remove: AskClaude tool (breaking)** — the deprecated, opt-in AskClaude tool, which let another pi model delegate a prompt to Claude Code, is gone, with its deprecation notice. The `askClaude` section of `claude-bridge.json` and the `askClaudeDeprecationShown` mark are now ignored, so an existing config still loads; while the global config still has `askClaude.enabled: true`, the first bridge turn of each session shows a warning naming the file to edit. Using Claude as the session model (`/model claude-bridge/...`) is unchanged; a pi subagent extension can stand in for the delegation.
- **Fix: tools whose parameters are a union of objects (upstream #250)** — a TypeBox `Type.Union` of object schemas has no root `type`, so the bridge rejected it while building its MCP server (`read: MCP tool parameters must be an object schema`), as with pi-better-edit's `read`. A root `anyOf`/`oneOf`/`allOf` whose branches are all objects is now accepted and flattened like the others; a schema with a scalar branch in any root combinator is still rejected. A property that `anyOf`/`oneOf` branches declare differently is advertised as an `anyOf` of every declaration instead of the first branch's, so `mode: "outline"` and `mode: "served" | "verbatim"` both reach Claude; a root or `allOf` declaration, which applies to every call, still wins.
- **Remove: Claude settings files in the repo and project-level config no longer apply (breaking, upstream #198)** — Claude Code's project and local settings (`.claude/settings.json`, `.claude/settings.local.json`) are no longer loaded by default on the provider path, so a cloned repo's hooks, `apiKeyHelper` and `env` don't run; `~/.claude/settings.json` still applies. Set `provider.loadClaudeSettings` to `"all"` (or `true`, which keeps its old meaning) in the global config to load project and local settings again. `false` still loads none on the provider path. A `provider` section in a project's `.pi/claude-bridge.json` is ignored, so a repo cannot change the executable, the settings sources or billing options. `CLAUDE_BRIDGE_CONFIG` names another file to use as the global config.
- **Fix: `--thinking off` turns thinking off (upstream #152)** — pi sends no reasoning level when thinking is off, so Claude Code applied its own default and kept thinking on. The provider and one-off paths now pass `thinking: { type: "disabled" }`, like pi-ai's Anthropic provider, except on models whose `thinkingLevelMap` marks `off` unsupported.
- **Fix: Claude Code no longer adds "The user hasn't heard from you in a while" reminders** — every Claude Code child runs with `CLAUDE_CODE_SILENT_TURN_REMINDER=0`; the message was not in pi's history and the user never saw it.
- **Fix: environment leaks to and from Claude Code (upstream #198)** — `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set only for Claude Code, not on pi's own process, so commands pi runs no longer inherit it. When pi is started from inside a Claude Code session, that session's markers (entrypoint, session id, env file, IDE port) no longer reach the bridge's Claude Code.

## 1.0.0 — 2026-11-09

- **Add: Fable 5.2 runs with 1M context** — pi-ai 1.5.1 lists `claude-fable-5-2` with a 1M window, but the bridge sent its bare id, which Claude Code 2.1.308 serves at 200K, so pi registered it at 200K. It now joins the measured-1M set and is sent as `claude-fable-5-2[1m]`, which served 1M on Pro without Extra Usage under both Claude Code 2.1.308 and 2.1.321 (`diag/CONTEXT-SIZE.md`). Its output reaches 128K with the bundled Claude Code 2.1.321 (see the SDK bump below); earlier versions do not know the model and cap it at 32K.
- **Remove: upstream mirror; the project is now developed independently** — `@viniciosrab/pi-claude-bridge` no longer rebuilds each upstream `pi-claude-bridge` release with its fixes; it continues from 0.9.4-fork.13 (upstream 0.9.3 plus this changelog's unreleased fixes) and takes no further upstream commits. `package.json` now carries the scoped name and this repository, a `vX.Y.Z` tag publishes through the new `release.yml` workflow, the user-facing README replaces upstream's (whose details moved to `docs/reference.md`) and credits it at the end, upstream's screenshots leave the package, the npm description no longer advertises the deprecated AskClaude tool, and the session-file warning links to this repository's issues.
- **Fix: Claude Code inserted "Continue from where you left off." when resuming an interrupted turn (upstream #145)** — resuming a session that ends mid-turn (an aborted tool call, a terminating tool, a discarded parked query) made Claude Code, behind a server flag, add its own continuation prompt ahead of pi's, which the model read as an instruction and which changed the cached prefix. `CLAUDE_CODE_RESUME_INTERRUPTED_TURN_MAX_AGE_MS=1` now counts every such turn as too old to continue; the abort-resume path still resumes Claude Code's own file with its history intact.
- **Fix: the turn after an API error re-cached the whole conversation (upstream #103)** — every error result (overloaded, rate limit, 5xx, quota) dropped the session, so the next turn rebuilt Claude Code's session from pi's history into a new file and re-cached all of it, once per retry. Claude Code has already recorded the failed prompt and an API-error record it leaves out of later requests, so the error now leaves the same mark as an abort, and the next turn resumes CC's own session file: a new prompt resumes it plainly, and pi's automatic retry of the same prompt resumes it at the entry before the failed prompt (`resumeSessionAt`), so the prompt is sent once. Offline, real CLI: same session id, no new `.jsonl`, the earlier `[user, assistant]` prefix of the request unchanged. A failure without a result (a CLI crash or SDK exception), a steer still pending, tool calls already run in the failed turn, a prompt CC never recorded, a CLI still alive past the 3 s bound, or a next context that is neither a new prompt nor the same one still rebuilds as before. The mark is kept in `claude-bridge-mirrors/`, so the resume also works after `/reload` or in a new process.
- **Fix: a user's Claude Code output style replaced pi's persona (upstream #220)** — an output style set in Claude Code's user, project or local settings is persona text written for standalone Claude Code, and the provider path applied it on top of pi's. Provider queries now pin `outputStyle: "default"` in the flag settings layer, which outranks the others; AskClaude keeps the user's style.
- **Fix: a tool call pi never received hung the turn (upstream #226)** — Claude Code waits in the bridge's MCP handler for every tool call it dispatched, and only pi can answer them, so a call lost between the two (for example a parallel call dropped after a non-streaming fallback) left the turn on "Working" until aborted. A handler now checks two minutes after it parks that pi has its call, and re-checks every two minutes while it waits; if pi never got it, the query is killed, the session mirror is marked for rebuild, the waiting stream ends with an error naming the tool and call id, the user gets a notice, and `claude-bridge-diag.log` gets a `lost_tool_call` entry. A call pi did receive is never failed, however long its tool runs.
- **Fix: queued steering keeps MCP input open through later turns (upstream #172)** — Claude Code's input now stays open until each steer is replayed into a turn, then closes after that turn completes, so a steer's tool calls no longer lose their MCP connection. An error result still ends the query, so a steer Claude Code had queued can no longer run on and replace the failure; the failed query drops the session mirror, and the next turn rebuilds it.
- **Fix: parallel tool calls lost after a non-streaming fallback (upstream #225, issue #237)** — when a stalled stream made Claude Code retry without streaming and the answer held several tool calls, pi got only the first while Claude Code waited on all of them, so the turn hung until aborted. Such an answer arrives as one `assistant` message per block under one id with nothing marking the last; its blocks now accumulate into the turn, and its tool-use stop waits until 100 ms pass with no further block (or the SDK moves on, or the query ends). An error result in that window still fails the turn. Streaming turns are unchanged.
- **Fix: teardown rewrote a finished tool-call turn (upstream #181)** — an abort, crash or error after a turn ended on a tool call changed pi's copy of that message to aborted/error, which could later orphan its tool result on Codex. Teardown now fails only a turn whose stream is still open; the abort-resume mark is recorded as before.
- **Fix: `pi -p` never exited after a `terminate: true` tool (upstream #210)** — the Claude Code query stayed parked on the tool result after pi's run ended, keeping the process alive with an orphan `claude` child. `session_shutdown` now closes that pi session's parked queries; other sessions' queries and the abort mark kept for a later resume are left alone.
- **Fix: the bash timeout broke the prompt cache on rebuilds (upstream #203)** — the bridge wrote a `timeout: 120` into every bash call pi stored, so a rebuilt session no longer matched what Claude Code had sent and missed the cache from the first bash call. The default is now set only on the copy pi executes.
- **Fix: a turn after an extension shortened the history ran without it (upstream issues #77, #55)** — a shorter history than the Claude Code session held was always treated as a subagent query and ran with no history at all; an extension that prunes or folds history in place then lost the whole conversation silently. Only a query reentrant on the same pi session takes that path now; any other turn rebuilds Claude Code's session from pi's history. Based on @shaneconner's patch, with reentrancy checked per pi session.
- **Fix: `/fork` and `/clone` re-cached the whole conversation** — the new pi session had no Claude Code session, so its first prompt rebuilt one from pi's history, which lacks the context blocks CC writes at its head; only the system prompt and tools were read from the cache. Each completed turn now records where it left CC's session file, and the forked session's first prompt starts from the SDK's `forkSession` copy of the parent's CC session, cut at the turn the fork keeps, under a new CC session id. The parent's file is never written. Anything that does not match (another cwd, history that is not a completed turn of the parent, an aborted turn, a file gone or rewritten, another live process) rebuilds as before. Live, haiku, 22k-token conversation: `/clone` read 21,684 and wrote 87; `/fork` before the third prompt read 21,681 and wrote 605, the kept last answer plus the new prompt (`diag/probe-fork-cache.mjs`).
- **Fix: a session continued in a new window re-cached the whole conversation** — a new pi process (a new window, `pi --continue`, `/resume`) had no record of the Claude Code session the pi session used, so its first prompt rebuilt that session from pi's history and re-cached everything (live: 22,392 tokens written vs 40 now). Each completed turn now records its CC session in pi's agent dir (`claude-bridge-mirrors/`), and a new process resumes it while pi's history still matches, CC's file exists, and no other running process uses it; otherwise it rebuilds as before.
- **Fix: the turn after an abort re-cached the whole conversation** — an abort made the next prompt rebuild Claude Code's session from pi's history, and a rebuilt file lacks the context blocks CC writes at its head, so the first request missed the cache from `messages[0]` (live: 22,419 tokens written vs 108 now). Once the aborted CLI has exited (live: 40–75 ms after the abort, its last write before the exit), the next prompt resumes CC's own session across the aborted turn, as native Claude Code does after Esc; a prompt sent while it is still shutting down waits for the exit, up to 3 s after the abort. A CLI still alive past that, a history rewrite, a user message CC never saw, or an aborted prompt CC never recorded still rebuilds as before; where the exit cannot be observed, a fixed 3 s settle window decides. Aborting that next prompt while it waits ends it without touching the session. The abort is recorded in the session's `claude-bridge-mirrors/` file, with the aborted CLI's pid and start time, so the same resume holds after a `/reload` or in a new process (live: 88 tokens written vs 46,351); the first prompt there polls for the CLI's exit within the same bound, and a reused pid does not pass for it. The bridge now launches the CLI itself (the SDK's `spawnClaudeCodeProcess`) to watch its exit, and still appends the CLI's stderr tail, with tokens and keys redacted, to `Claude Code process exited …` errors.
- **Bump: Claude Agent SDK 0.3.321 (Claude Code 2.1.321)** — Claude Code's new per-request log in session files (2.1.308+) is turned off; it made them about a third larger. 2.1.321 knows Fable 5.2, so its answers can use 128K output tokens instead of the 32K Claude Code allows a model it does not know.
- **Fix: abort ignored after a terminated tool batch (#200, issue #199)** — when a run ended with Claude Code's query parked at a tool call (`terminate: true`), aborting the next run did nothing. Each run that continues the query now binds its own signal. Thanks @orshih6 and @cootue.

## 0.9.3 — 2026-10-13

- **Fix: Haiku 5.5 registered at 1M (#190)** — Thanks @Blue-B.
