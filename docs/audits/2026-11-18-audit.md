# Audit: pi-claude-bridge

- **Date:** 2026-11-18
- **Commit:** `f34e9e0` (the merge of PR #54 on `main`)
- **Scope:** the whole repo: `src/` (all of it, split across five read-only auditors, with the main findings checked again by a sixth that tried to refute them), `tests/`, `diag/`, `docs/`, CI and release workflows, `package.json`.
- **How it was checked:** every finding was read in the code, with its callers traced. Nothing was reproduced by running it. Baseline on a clean copy of this commit: `npm ci`, `npm run typecheck` passes, `npm run test:unit` passes 565 of 565.
- **Previous audit (2026-11-10):** 13 of its 18 findings are fixed or gone (AskClaude was removed). Still open: #6 (finding 3 below), #8 (finding 7), #12 (finding 10). #15 (empty thinking with no effort) was dropped: pi raises a model's `off` level to `minimal`, so pi itself never reaches that case.

What this repo does: It is an extension for the `pi` coding agent. It lets pi use Claude through a Claude Code subscription: Claude Code talks to Anthropic, pi runs every tool through a small in-process tool server, and the bridge keeps a copy of pi's conversation in Claude Code's session files so the prompt cache (the saved, cheaper part of a request) stays warm.

Load assumed: one developer on one machine. One pi process serves several pi sessions at once (a parent and its subagents), and several pi windows can share the same files on disk.

## Must fix

1. **A tool call answered by another provider leaves Claude Code waiting for good** (`src/index.ts:L1170-1180`, `L2298-2299`, `L2419-2420`, `L2480`, `L2501`)
   - **What this is:** When Claude calls a tool, the Claude Code query "parks": it waits for pi to send the tool result back. A watchdog fails a call pi never received.
   - **Problem:** The user runs `/model` to a non-Claude provider while the tool runs. pi picks the model per request, so the tool result goes to the other provider and never comes back. The watchdog re-arms every 120 s forever, because pi did receive the call. Nothing else discards the query before `session_shutdown`. Every later Claude prompt in that session sees a running query, so it is handled as "reentrant" (a query started inside another one): the system prompt check is skipped, so a changed prompt never reaches Claude, and a turn that continues at a tool result writes on stdin again, which brings back the "No response requested." bug (#274).
   - **Fix:** In the fresh-query path, before computing `isReentrant`, call `discardQuery` on every active context of the same pi session whose parked tool calls already have a `toolResult` in `context.messages` (pi has moved past them). Add one unit test: park a call, deliver its result through the history only, send a new prompt, check the old query is closed and the new one is not reentrant.
   - **If we skip it:** One Claude Code process leaks per switch, and the rest of that session silently ignores prompt changes and can end turns early.

## Should fix

2. **A refused model switch is tried again at every tool call of the turn** (`src/index.ts:L1987-2027`, `L2333-2341`)
   - **What this is:** New code: when the model changes while a tool runs, the bridge asks the running query to switch (`setModel`) before it delivers the result, and waits up to 15 s.
   - **Problem:** When `setModel` fails (for example Mythos on an account without access), `switchingTo` is cleared and `servedModel` stays the old model. At the next tool result the two still differ, so the bridge calls `setModel` again. A turn with 30 tool calls makes 30 failed validation requests, each one holding back a result. The changelog says the turn finishes on the old model.
   - **Fix:** Store the refused model on the query context (`refusedModel = cliModel`) and skip a switch to that same model. A fresh query starts with it empty. Add a second tool boundary to the "refuses" test in `tests/unit-model-switch-mid-turn.mjs`.
   - **If we skip it:** Long turns get slower after a bad `/model`, with one wasted API call per tool.

3. **Resuming after an abort still throws away the saved fork points** (`src/index.ts:L2143-2149`; effect in `src/fork.ts:L593-608`, `L726-735`) — *previous #6, still open*
   - **What this is:** The "mirror" file records where each finished turn ends in Claude Code's session file, so a `/fork` can reuse the cache up to that point.
   - **Problem:** `resumeAfterAbort` deletes the mirror. Ten finished turns, Esc on turn 11, then turn 12: the new mirror holds only turn 12. A `/fork` at turn 5 finds no fork point and rebuilds the whole conversation. While turn 12 runs there is no mirror at all, so a pi restart mid-turn also rebuilds.
   - **Fix:** Instead of `dropMirror`, write the mirror again without the abort fields and keep `turns`. Claude Code only appends to its file, so the old turn ends stay valid. Add an abort-then-fork case to `tests/unit-fork-cache.mjs`.
   - **If we skip it:** One Esc in a long session makes every earlier `/fork` pay the full cache again.

4. **A tool with a bad schema throws after the turn has already changed state** (`src/index.ts:L2434`, `L2502-2505`, `L2543-2544`; `src/mcp-server.ts:L55-60`)
   - **What this is:** Each pi tool becomes a Claude Code tool. A tool whose parameters are not an object (for example `Type.Any()`, or a union with a string branch) is rejected.
   - **Problem:** The rejection happens at `buildMcpServers`, after the turn has claimed pi's stream, synced (and maybe rebuilt) the session file, used up the "history was rewritten" mark and queued the prompt. There is no try/catch, so `streamSimple` throws instead of ending its stream with an error. The stream and prompt are left half-set on the shared context, and the used-up mark means a rebuild the next turn needed is skipped.
   - **Fix:** Build the tool servers right after `resolveMcpTools` (`L2423`), before anything else, and turn a failure into an `error` event on the stream, like the other early errors at `L2290`. One test through `streamSimple` with a bad tool.
   - **If we skip it:** One badly typed tool from any extension breaks every Claude turn in an unclear way, and leaves state behind.

5. **A second query in the same pi session can rewrite the file the first one is still writing** (`src/index.ts:L861-899`, `L902-936`, `L2480-2502`, `L2721-2739`)
   - **What this is:** `syncSharedSession` picks how a query starts: resume Claude Code's file (REUSE), rewrite it under the same id (REBUILD), or start fresh.
   - **Problem:** A reentrant query of the same pi session only gets its own throwaway id when its history is shorter than the saved position. With the owner's full history plus a tool call, it takes REBUILD with the same id, and `deleteSession` (`L930`) deletes the file the parked Claude Code process is writing. With one message less it resumes the same id, so two processes append to one file. Its end also writes its own position and prompt digest into the owner's state. Not proven: whether any real extension calls the model with its own session id during a tool. `tests/int-tool-message.mjs:L248-251` already notes this path as untested.
   - **Fix:** In `syncSharedSession`, when `isReentrant` and the session already has a file, never resume or rewrite it: import the history under a new id and return `{ sessionId, preserveSharedSession: true }`. The end of the query (`L2721-2727`) already deletes such a throwaway session.
   - **If we skip it:** If it happens, Claude Code's file breaks silently, and the next resume can follow the wrong branch or lose the last turn.

6. **A fresh start after `/tree` rebuilds the new session on its second turn** (`src/index.ts:L902-908`, `L2735-2739`)
   - **What this is:** After `/tree` or `/compact`, the session is marked "needs rebuild".
   - **Problem:** Going back to the first prompt and sending gives a "clean start", which clears the old state only when an error was recorded. The end of the turn copies `needsRebuild: true` (and old abort fields) into the new session's state. Turn 2 then rewrites the brand-new file and misses the cache once. The same case with an error was fixed and pinned (`tests/unit-error-resume.mjs:L383-387`); this one has no test.
   - **Fix:** At the clean start, clear the old state whenever there is one and the query is not reentrant: `if (sharedSession && !isReentrant) { setSessionStateFor(piSessionId, null); if (piSessionId) dropMirror(piSessionId); }`. One test next to the error case.
   - **If we skip it:** Each return to the root costs one full cache rewrite, with no visible sign.

7. **A session stays "owned" by a window that already left it** (`src/fork.ts:L500`, `L690`, `L701`, `L843`) — *previous #8, still open*
   - **What this is:** The mirror records the pid of the pi process that wrote it, and another process will not use a mirror whose pid is alive.
   - **Problem:** Window A uses session S, then switches to T. Window B opens S and rebuilds, because A is alive. After a reboot, an unrelated process can hold the same pid. The check in `forkPoint` (`L843`) blocks without protecting anything, since `turnEndEntry` (`L785-811`) already checks the file's header and size.
   - **Fix:** Record `startTime: cliStartTime(process.pid)` with the pid and check both, like `cliAlive` already does for Claude Code processes. Delete the check at `L843`. Update `tests/unit-fork-cache.mjs:L225`, which pins today's behavior.
   - **If we skip it:** Opening a session in a second window rebuilds it with no visible reason.

8. **Two Claude Code settings leak into every command pi runs** (`src/fork-tool-streaming.ts:L18-23`; `src/fork.ts:L104-115`)
   - **What this is:** The bridge gives each Claude Code child its environment through `ccChildEnv`. The changelog (upstream #198) says child-only variables stay out of pi's own environment "so commands pi runs no longer inherit it".
   - **Problem:** Loading these two modules writes `CLAUDE_CODE_ENABLE_FINE_GRAINED_TOOL_STREAMING=1` and `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH=1000000` into pi's `process.env`. A `claude -p` run through pi's bash tool, or another extension's child process, inherits both; the second one even overwrites a value the user exported. The comments say this avoids editing `CC_CHILD_ENV` "which upstream owns", which stopped being true at 1.0.0.
   - **Fix:** Add both in `ccChildEnv` (`src/index.ts:L89-96`), keeping a user value for the first: `{ [TOOL_STREAMING_ENV]: "1", ...env, ...CC_CHILD_ENV, ...FORK_CHILD_ENV }`. Delete `applyToolStreamingEnv` and `applyForkChildEnv`, and point `tests/unit-fork-tool-streaming.mjs:L43-49` and `tests/unit-fork.mjs:L145` at `ccChildEnv()`.
   - **If we skip it:** Commands and other tools run with Claude Code flags nobody chose.

9. **The secret filter for Claude Code's error output misses common forms** (`src/fork.ts:L212-216`)
   - **What this is:** When Claude Code fails, its stderr goes into the error message that pi shows and stores in the session. A regex hides tokens first.
   - **Problem:** The pattern needs a word boundary (`\b`) before `token`. In `ANTHROPIC_AUTH_TOKEN=abc123` the `_` before `TOKEN` is a word character, so there is no boundary and nothing is hidden. In JSON, `{"access_token":"abc"}` and even `{"token":"x"}` have a quote before the colon, which the pattern does not allow. Only `sk-ant-…` values are always hidden. Whether Claude Code prints such forms was not checked.
   - **Fix:** Use `(?<![A-Za-z0-9])` instead of `\b` and allow an optional quote before `[=:]`. Add these three strings to the test in `tests/unit-abort-resume.mjs:L419-433`.
   - **If we skip it:** A gateway or OAuth token printed by Claude Code can end up in pi's session file in plain text.

10. **`attrib.py` still credits a subagent's failure to its parent** (`diag/attrib.py:L85-93`) — *previous #12, still open*
    - **What this is:** A diagnosis script that counts which queries fail with Extra Usage, from the debug log.
    - **Problem:** A failing query logs two lines (`error result`, then `for-await loop exited`) and the script pops its stack on both. Parent P waits on a subagent C in the same process; C fails: the first line pops C, the second pops P and marks it "ok", and P's own failure later finds an empty stack and is not counted. The stack key is the module instance id, not the session id its docstring names.
    - **Fix:** On the error line, only set the outcome of the top entry; pop only on `for-await loop exited`. Fix the docstring.
    - **If we skip it:** The "agent lifecycle" numbers in `diag/EXTRA-USAGE-400.md` undercount subagent failures.

11. **`change-case` is a runtime dependency only tests use** (`src/convert.ts:L6`, `L54`)
    - **What this is:** `pascalCase` turns a pi tool name into a Claude Code one when no name map is given.
    - **Problem:** The only production caller (`syncSharedSession` → `convertAndImportMessages` → `convertPiMessages`) always passes the map, even an empty one. Only tests and diag scripts call without it, and no test checks `pascalCase`'s output. Every user still installs the package.
    - **Fix:** Use the name unchanged (or upper-case the first letter) on that path and remove the dependency.
    - **If we skip it:** One dependency to install, update and trust for no production use.

12. **Leftovers: dead branches, an unused peer dependency, a broken script, misplaced comments** (several files)
    - **What this is:** Code and notes that nothing uses or that describe something else.
    - **Problem:**
      - `runIsolatedSummary`'s non-summary branch and `extractIsolatedSummaryPrompt` (`src/index.ts:L540-550`, `L625-634`) never run: the only production caller (`L2272-2274`) passes `cacheRetention: "none"`.
      - `__test.promptDigestFor` (`L1010`) is used nowhere.
      - `piToolNameFor` (`L1036-1038`) only wraps a `Map.get`.
      - `typebox` is a peer dependency (`package.json:L51`) that nothing in `src/` imports since AskClaude was removed, but npm 7+ installs it for every user.
      - `diag/prompt-churn.mjs` reads `claude-bridge-captures/` by default, which activation now deletes, so it dies with ENOENT; its header calls it historical and its result is in `EXTRA-USAGE-400.md`.
      - The doc comment of `deliverToolResults` sits on `SWITCH_MODEL_WAIT_MS` (`L1965-1978`), the one of `syncSharedSession` sits on `verifyWrittenSession` (`L729-733`), and the `forceRotate` comment (`L236-238`) says orphan writes land on a dead inode, while the file is never deleted.
    - **Fix:** Delete the dead branch, the helper, the export, the peer entry and the script; move the two doc comments to their functions; fix the `forceRotate` comment.
    - **If we skip it:** About 100 lines to read and keep in sync, and an extra package for every install.

## Nice to have

13. **A timing assertion can fail CI at random** (`tests/unit-model-switch-mid-turn.mjs:L182-188`)
    - **What this is:** A test checks that a slow switch does not hold the tool result.
    - **Problem:** `Date.now() - started < 250` also counts query setup, and `node --test` runs files in parallel with tests that start the real CLI. Under load the setup alone can pass 250 ms. The next line (`setModels` still empty when the result arrives) already proves the rule. CI already had a flake of this kind (#40).
    - **Fix:** Delete line 184.
    - **If we skip it:** Now and then a PR is blocked by a failure with no bug behind it.

14. **A tool named `Read` steals the mapping of a tool named `read`** (`src/index.ts:L1151-1156`)
    - **What this is:** Tool names are also stored in lower case, so a call in the wrong case can be matched.
    - **Problem:** With tools `[read, Read]`, the lower-case alias of `Read` overwrites the exact entry for `read`. On a rebuild, a `read` call in the history is written as `mcp__custom-tools__Read`.
    - **Fix:** Write the lower-case alias only when the key is still free.
    - **If we skip it:** Rare, but the rebuilt history then names the wrong tool.

15. **Shutdown tells parked tool calls "Context was compacted"** (`src/index.ts:L1104`, `L2197-2201`)
    - **What this is:** At `session_shutdown`, parked queries are closed.
    - **Problem:** They are closed through `discardRewrittenQuery`, which answers "Context was compacted; this query was discarded." and logs "history rewritten under a parked query". Neither is true at shutdown, and it misleads anyone reading the debug log.
    - **Fix:** Call `discardQuery(c, "Session shut down; this query was discarded.")`.
    - **If we skip it:** Wrong notes in logs when a shutdown is being debugged.

16. **`markRebuildHooks` grows on every `/reload`** (`src/index.ts:L328-332`, `L370`)
    - **What this is:** A set on `globalThis`, so every loaded copy of the module learns about a `/compact` or `/tree`.
    - **Problem:** Each module load adds its hook and nothing ever removes one. Each dead hook keeps the old module's maps and streams in memory.
    - **Fix:** `markRebuildHooks.delete(markRebuildForSession)` in the `session_shutdown` handler.
    - **If we skip it:** Memory grows a little with each reload in a long pi session.

17. **`attachment-coverage.mjs` reports MISPLACED when an attachment was only dropped** (`diag/attachment-coverage.mjs:L90-109`)
    - **What this is:** A diagnosis script that checks `@file` attachments land on the right message after a rebuild.
    - **Problem:** It compares expected and placed attachments by position. `placeCarriedAttachments` skips changed or ambiguous ones, so from the first skip on every pair is shifted, and the script exits 1 with "resolved, but to the wrong message", the opposite of what happened.
    - **Fix:** Match by identity (map each attachment object to its `afterIndex`), not by index.
    - **If we skip it:** The tool raises a false alarm exactly in the cases the last attachment fix added.

18. **The release publishes any `v*` tag, even off `main`** (`.github/workflows/release.yml:L6-9`)
    - **What this is:** Pushing a tag publishes to npm as `latest`, after checking the tag matches `package.json` and running the unit tests.
    - **Problem:** A tag on an unmerged branch commit with the same version passes every check and publishes code that never went through `main`.
    - **Fix:** Add a step `git merge-base --is-ancestor "$GITHUB_SHA" origin/main` (with `fetch-depth: 0`).
    - **If we skip it:** Safe releases rely only on following the manual steps in `AGENTS.md`.

5 smaller findings were left out: a substring check for an aborted prompt that a short prompt could match (trigger not proven), mirror pruning that runs once per process, a debug-only map that only grows, a rejected tool call that stays as an empty row in pi's TUI until reload (needs a pi change), and the previous audit's #15.

Verdict: Mostly healthy and well tested (565 unit tests pass); fix 1 first, then 2 and 3.

Lean: -110 lines, -2 dependencies possible.
